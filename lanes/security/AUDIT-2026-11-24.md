# Security audit, 2026-11-24 (full site, before outreach)

Cam: "make sure the whole site is secure: people can't hack the website, can't steal information, can't break into passwords, can't steal API keys."

Run against `main` at `67a8f81`, locally only. Nothing in production was touched, and no secret values or customer data were read or written here.
- Sign-in doors and access control were each swept by a `security-auditor`. The Security lane spot-checked H1, M3, M14 and the lockout race in the code.
- The Security lane did these itself: secrets and the browser bundle, input handling, webhooks, crons, headers and CSP, dependencies, logs and public-form limits.
- Secrets were checked against a real `next build`. Every secret env var was set to a canary value, then the browser output (`.next/static`) was searched for those values.
- Previous reports: `prelaunch-2026-11.md` (11-16) and `2026-11-10-full-sweep.md`. An id in brackets is the 11-16 id.

| Severity | Count | Short answer to Cam |
|---|---|---|
| Critical | 0 | No API key or secret reaches the browser, the repo, logs or responses. No route lets an outsider in. |
| High | 1 | One course can copy golfer contact details that belong to another course (until the pre-launch wipe). |

## High

### H1. Member import or add copies a GreenReserve golfer's name and phone into another course (was H1, still open)
- **Files:** `src/lib/member-import.ts:25,36,46-49`, `src/app/api/operator/members/route.ts:142-179`.
- **Exploit:** a login with `members.edit` at course A uploads a CSV of email addresses with no names.
  - Every address that has a `GolferAccount` becomes a linked membership, with the name and phone copied from that account.
  - The single add returns `golfer{firstName,lastName,email,phone}`. With `payFirst`, no email goes out, so the golfer never knows.
  - The skip reason ("No name, and no GreenReserve account to take it from") also tells course A which addresses have no account.
- **Limit:** `GolferAccount` has no writers left (golfer sign-in was retired on 11-18) and is in `WIPED_TABLES`. After the pre-launch wipe, there is nothing to pull. Until then it is live.
- **Fix:** never link or copy from `golferAccount` on add or import. Make an invite row with only the name and phone the course typed, and require a name on every row. Member pricing still matches on the golfer's verified email (`getGolferMembership`).

## Medium

### M1. Cancel ignores the charge lock (was M1)
- **Files:** `src/lib/cancel-booking.ts:225-237` (the only guard is `status:'confirmed'`), `src/lib/checkin-booking.ts:490` (an unconditional `booking.update`).
- **Exploit:** a golfer cancels while staff or the pay link are charging the booking. The golfer can end up paying for the round plus a hold or late fee. Or the round is refunded while the booking stays paid.
- **Fix:** return `BEING_CHARGED` before any Stripe call, and add `...notBeingCharged()` to the cancel's `updateMany`. Make check-in's final write conditional on the booking still being confirmed, and refund on a miss.

### M2. Anyone can verify an unverified course owner's email without the link (new)
- **File:** `src/app/api/auth/verify/route.ts:5-9`.
- **Exploit:** `POST {"token":{"not":""}}`. The JSON body goes straight into `findFirst({ where: { verificationToken: token } })`. Prisma reads the object as a filter, so the call matches the first operator with any pending token and marks that email verified. Repeat it to work through every pending operator.
  - `emailVerified` is a go-live precondition.
  - The route has no rate limit.
- **Fix:** accept only a 64-hex string, and add a rate limit. The same type check goes on every public route that puts a body value into a filter-taking query. This is the only public one the sweep found.

### M3. The per-account lockout can be raced, and the race shows which emails have accounts (new)
- **Files:** `src/app/api/admin/login/route.ts:54-58`, `src/app/api/auth/login/route.ts:54-58,89-93`, `src/app/api/cam/login/route.ts:230-234`.
- **Exploit:** send about 6 wrong passwords for one email at the same moment.
  - On a real account, each request writes `read + 1`, so the counter goes up by 1 and the account never locks. The 5-try lockout stops limiting guesses (the per-IP cap still applies).
  - An unknown email counts atomically (`login-guard.ts`), so it answers 429 where a real account answers 401. That breaks the SEC-3 promise that no sign-in says whether an email has an account.
- **Fix:** an atomic `{ increment: 1 }` that returns the count, and lock on the returned value.

### M4. Change-password has no guess limit, and the operator version brings a killed session back to life without 2FA (new)
- **Files:** `src/app/api/operator/change-password/route.ts:9,21,30-37`, `src/app/api/admin/change-password/route.ts:9,21`.
- **Exploit:** a thief holds a stolen `gr_operator` cookie. The owner resets their password to kick the thief out.
  - `getOperatorSession()` doesn't check `sessionVersion`, so the old cookie still works on this route.
  - The thief can guess `currentPassword` without limit. A hit mints a fresh, valid cookie with no 2FA.
  - The admin route also has no guess limit.
- **Fix:** use the `sv`-checking session helper; cap tries per account; write `securityEvent` for a wrong password and for `password_changed`.

### M5. Admin employee sessions survive a password change or reset for up to 12h (was M3)
- **Files:** `src/lib/admin-session.ts:129-134,190-193`. `AdminUser.sessionVersion` exists but nothing reads or writes it, and employee logout only clears the cookie.
- **Fix:** put `sv` in the token, check it in `resolveAdminSession`, and bump it on every password write and on logout.

### M6. The owner's authenticator can be replaced without a step-up (was M4)
- **File:** `src/app/api/admin/two-factor/route.ts:27-32,59-89`.
- **Exploit:** start, confirm and regenerate overwrite the secret and the recovery codes with no fresh second factor, no alert and no `securityEvent`. A stolen `gr_owner` cookie can swap in its own authenticator, which defeats every later step-up.
- **Fix:** require `stepUpRequired` (or `freshStepUpRequired`), write a `securityEvent`, and send an alert email.

### M7. Admin forgot-password shows which emails are admin accounts, and is capped only per IP (was M5)
- **File:** `src/app/api/admin/forgot-password/route.ts:9-41`.
- **Problem:** an unknown email answers instantly, while a real one waits on a send and can return 500.
- **Fix:** answer the same way every time and do the work in `after()`, cap per address, and write a `securityEvent`.

### M8. The 2FA attempt counter can be raced, and /cam resets it on every correct password (was M6)
- **Files:** `src/app/api/auth/2fa/verify/route.ts:36-52`, `src/app/api/auth/login/route.ts:66-67`, `src/app/api/cam/login/route.ts:24,161-184,296`.
- **Fix:** claim the attempt atomically before comparing, as member codes already do. Don't reset the counter on a password success. Cap codes issued per account.

### M9. Reset, setup and set-password tokens are stored in plaintext (was M7)
- **Files:** `src/app/api/auth/forgot-password/route.ts:22`, `src/lib/operator-setup.ts:21-25`, `src/app/api/auth/reset-password/route.ts`, `src/app/api/admin/forgot-password/route.ts:26-32`, `src/app/api/admin/login/route.ts:69-75`, `src/app/api/cam/login/route.ts:265-269`.
- **Risk:** anyone who can read the database (a leaked backup, a log of a row) can take over an account with the 7-day setup link.
- **Second problem:** admin set-password compares with `!==` and then writes with a plain `update`, so two submits of one token can both land.
- **Fix:** store a SHA-256 of the token and look it up by hash (no schema change; links that are out now stop working). Make set-password's write conditional.

### M10. GreenReserve fees and failed charges are shown to admin logins without the Money area (was M9) — Cam
- **Files:** `src/app/api/admin/course-detail/route.ts:83,157-161,188,202`, `src/app/api/admin/today/route.ts` + `src/lib/admin-today.ts:187` + `src/lib/admin-action-queue.ts:69-73`, `src/app/api/admin/courses/route.ts:178`, `src/lib/admin-ask.ts:95,118`.
- **Fix:** send those fields as null unless `hasArea(session,'money')`.

### M11. Round pay links and receipts can be sent without limit, and `send_receipt` goes to any number (was M10)
- **File:** `src/app/api/operator/bookings/route.ts:255-334`.
- **Exploit:** a login with `sheet.checkin` loops `send_receipt` with any `to` and `smsConsent:'verbal'`. Every call costs Twilio money and sender reputation.
- **Fix:** cap sends per course and per booking.

### M12. Server code was bundled into the dashboard's browser pages (new)
- **What happened:** a real build put `lib/stripe.ts` and `lib/prisma.ts` into the `/dashboard/money` and `/dashboard/events` browser chunks. `LedgerTab` and the event pages each imported one pure helper from a file that also imports the database and Stripe.
  - The demand-pricing card and the admin documents page had the same kind of chain.
- **No value leaked:** Next.js inlines only `NEXT_PUBLIC_` variables, so the key reads as undefined in the browser. The canary build had zero hits.
- **Why it still matters:** nothing stopped a future helper that reads a key at import time, or one `NEXT_PUBLIC_` slip.
- **Fix:** move the pure helpers into client-safe files, and add `scripts/client-bundle-test.ts`. It walks every `'use client'` import graph and fails on prisma, Stripe, server-only packages or any non-public env var.

### M13. Next.js 15.5.28 has three moderate advisories, fixed in 15.5.29 (new)
- **Advisories:** GHSA-f3mh-rxg3-f5g2 (HttpOnly cookies exposed through a response header on Edge runtime routes), GHSA-7qx7-33qx-rqx2 (an SVG bypass in image optimization), GHSA-pc58-hwjq-p385.
- **Why it applies:** `src/middleware.ts` runs on the Edge runtime and reads `gr_operator`.
- **CI:** the gate fails only on high, so this passes it today.
- **Fix:** bump to `^15.5.29`.

### M14. Operator and admin login show which emails have accounts when the password is not a string (was M2)
- **Files:** `src/app/api/auth/login/route.ts:54,89`, `src/app/api/admin/login/route.ts:54`.
- **Exploit:** `{"password":123}` on a real account reaches `bcrypt.compare` and returns 500. An unknown email returns 401.
- **Fix:** refuse a non-string password with 400 before any lookup.

## Low

- **L1. Five operator routes skip the `sessionVersion` check** (was L1): `operator/my-courses`, `active-course`, `onboarding-complete`, `change-password` (see M4) and `auth/resend-verification`. Fix: use the `sv`-checking helper.
- **L2. Some doors refuse or admit without a `securityEvent`** (was L2, partly fixed):
  - 2FA verify refusals;
  - admin set-password refusals;
  - `inquiries/signin-code` and `signin-verify`;
  - `password_changed` on operator change-password and on the owner reset;
  - a wrong current password on both change-password routes.
- **L3. Any staff login can mint the 30-day preview token** (was L3). File: `src/app/api/operator/preview-link/route.ts:9-17`. Fix: owner only.
- **L4. Taking a course offline or archiving it cancels and refunds every future booking without a step-up** (was L4) — **Cam** (question 1 from 11-16 is still open). Files: `admin/course-detail/route.ts:251-259`, `admin/archive-course/route.ts:42-49`.
- **L5. Concurrent identical admin refunds write duplicate refund rows, and hold refunds count against the round's cap** (was L5). Files: `src/lib/refund-booking.ts:80,116-119`, `stripe/webhook/route.ts:77`.
- **L6. A login with only `shop.sell` can void a cash sale** (was L6). File: `operator/shop-sales/route.ts:251-254`. Fix: require `sheet.counter_payment`.
- **L7. The staff setup email builds its HTML from an unescaped, course-chosen name, and sends with its own Resend client** (was L7). File: `admin/resend-staff-setup/route.ts:25,35`. Fix: `letterEmail()` and `getResend()`.
- **L8. `scripts/admin-areas-test.ts` only checks that `areaGate(` appears in the source** (was L8). Every M10 place passes it.
- **L9. Adding or inviting staff says whether an email is a login anywhere on the platform** (new).
  - Files: `src/lib/team.ts:415-421` (capped at 30 an hour) and the legacy `operator/staff` POST at `:68` (no cap).
  - Fix: the same answer either way; delete the legacy POST.
- **L10. Secret handling** (new):
  - `jwtVerify` doesn't pin `HS256` (`auth.ts:37`, `middleware.ts:20`, `admin-session.ts:170`, `owner-session.ts:139`, `member-session.ts:45,64`). jose already refuses `none` with a symmetric key, so there is no exploit today.
  - `JWT_SECRET` has no minimum length.
  - The cron bearer (`cron-auth.ts:33`) and the bootstrap key (`admin/bootstrap/route.ts:8`) are compared with `!==`.
  - Fix: pin the algorithm, refuse a short secret in production, and use `timingSafeEqual`.
- **L11. The member magic link signs in on a GET and can be reused for 15 minutes** (`member/[courseSlug]/verify/route.ts:23-66`).
  - The token sits in request logs.
  - It also allows a login CSRF: someone can send a person a link that signs them in as someone else.
  - Fix: make it single-use (a `jti` claimed in the RateLimit table), with a POST confirm page.
- **L12. Operator logout revokes nothing on the server** (`auth/logout/route.ts`). With the 7-day sliding renewal, a copied cookie lives until the next password change. Fix: bump `sessionVersion` on logout.
- **L13. Four log lines write full email addresses:**
  - `cron/send-reminders/route.ts:47`
  - `inquiries/route.ts:49`
  - `lib/two-factor.ts:50`
  - `admin/broadcasts/route.ts:119`
  - No log writes a code, token or link. Fix: log the row id instead.
- **L14. The per-IP rate limits key on the left-most `X-Forwarded-For`** (was U1; `src/lib/rate-limit.ts:61-64`, `owner-session.ts:39`). Vercel says it overwrites the header, so this is likely not exploitable there. Fix: prefer `x-vercel-forwarded-for` / `x-real-ip`, as `evidentiaryIp` already does.
- **L15. UNVERIFIED: the Stripe reconciliation's expected fees include test courses** (`admin/platform-stripe/route.ts:42-45`, no `ON_REAL_COURSE`). This only matters if a test course takes live charges.

## Accepted as they stand (no PR)

- **Cal.com webhook replay.** Cal.com signs no timestamp, so a replay can't be refused by age. Every branch is idempotent on the booking uid.
- **Twilio inbound.** Signed. A replayed STOP or START changes nothing.
- **The full CSP is still report-only, with `script-src 'unsafe-inline'`.** This is as SEC-1 decided: it gets enforced once its reports are clean. That needs nonces and a read of Sentry's CSP reports, which is a separate job.
  - The Cal.com embed (`app.cal.com` script and frame) is in the report-only policy and runs only on the homepage, which holds no session.

## Checked and clean

### Secrets
- No canary value in the browser output.
- The only `NEXT_PUBLIC_` variables are the Sentry DSN, the Stripe publishable key and the site URL.
- No keys are committed, in the tree or in the history the clone holds; the test files use fakes.
- `.env*` is ignored.
- No response or log carries a key.
- Sentry's data collection is all off (SEC-2).

### Webhooks
- **Stripe:** `constructEvent` (signature plus its 5-minute tolerance).
- **Twilio:** `validateRequest` over our fixed URL.
- **Cal.com:** HMAC with `timingSafeEqual`, and the secret is required.
- **Resend:** there is no Resend webhook.

### Crons
- All six use `cronRoute`, which fails closed with no `CRON_SECRET`, and all six are in `vercel.json`.
- The admin re-run builds the request inside the server and refuses the charging jobs.

### Headers
- HSTS, nosniff, `X-Frame-Options: DENY`, a trimmed referrer, a Permissions-Policy, and an enforced `frame-ancestors 'none'; base-uri; object-src`.
- `poweredByHeader` is off.

### Input
- **SQL:** no raw SQL takes input. The `$queryRawUnsafe` calls in `data-reset.ts` use constant table names, and every other `$queryRaw` is tagged.
- **Page HTML:** `dangerouslySetInnerHTML` appears only for a server-made QR SVG, the agreement Markdown from disk, and constant JSON-LD.
- **Email HTML:** every email goes through `letterEmail()`, which escapes every string and allows only http(s)/mailto links. The only exception is L7.
- **Alert pages:** escaped.
- **SSRF:** every server fetch goes to a fixed host (Census, weather.gov, GitHub, Resend, Sentry, Stripe, our own URL).
- **Uploads:** image or PDF allowlists with size caps, stored on the separate blob host. Private files go through the `isBlobStoreUrl` host check.

### Redirects
- The log-in `back=` uses `safeBack`: same-origin, resolved path, encoded dots refused.
- Short links redirect only to our own path. Codes are 50 random bits, rate-limited, and expire.
- The operator login's redirect comes from the server.

### Sign-in
- Cookie flags and lifetimes match the session table.
- JWT secrets fail closed in production, and every verifier checks the token `type`.
- `/cam`: password, then device, then second factor. Passkeys are single-use. TOTP replay is guarded. Recovery codes are hashed. Device approval is SHA-256, 15 minutes and single-use.
- Member codes and inquiry codes: HMAC, `timingSafeEqual`, attempts claimed atomically.

### Access control
- All 105 operator route files gate with `requirePermission`, refuse staff, or are owner-only.
- Every id from a request is checked against the session's course before use.
- Every admin route has a role check plus `areaGate`, or is owner-with-2FA only.
- The 18 routes the code map marks `NONE FOUND` are all guarded by a helper (`teamOwner`, `writeGate`, `companyDocsGate`, `loggedInAt`).

### Public tokens
- Booking tokens are UUIDs; alert tokens are 24 bytes; call links are 48 hex.
- Pay, statement and event tokens are UUIDs, and the empty-token case is refused.

### Public form limits
- **Contact us** (`/api/inquiries`): 5 an hour per IP, plus a honeypot.
- **Alerts:** 10 per 5 minutes per IP, and 20 an hour per email.
- **Booking:** 30 an hour per IP, and 10 an hour per email.
- **Event sign-up:** 10 per 10 minutes per IP, and 300 an hour per event.
- **Promo check:** 30 an hour.
- **Setup intent:** 10 an hour per IP, and 8 an hour per email.
- **Inquiry codes:** 6 an hour per IP, and 3 per inquiry.
- **Upload:** 20 per 5 minutes per IP.
- **`/api/waitlist`:** retired (410).

### Dependencies
- `npm audit --omit=dev`: only M13.
- The CI gate, Dependabot and the SEC-4 allowlist (empty) are unchanged.
